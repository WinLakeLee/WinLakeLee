## 1. 인증 & 세션

| P | 항목 | 내용 |
|---|---|---|
| P0 | 패스워드 해싱 | **Argon2id** (memory ≥ 64MB, iterations ≥ 3, parallelism ≥ 4). bcrypt/scrypt 폴백 금지, 평문·가역 저장 절대 금지 |
| P0 | JWT 수명 | Access Token 15분 이하, 서명 알고리즘 **RS256/EdDSA 고정**(`alg: none`·HS256 다운그레이드 거부), `kid` 기반 키 롤테이션 지원 |
| P0 | Refresh Token Rotation | 매 갱신 시 기존 토큰 폐기 + 신규 발급(ERD §2). **재사용 감지 시 해당 유저 전 세션 강제 만료** — 탈취 대응 |
| P0 | 토큰 저장 | Refresh Token은 SHA-256 해시로만 저장(원문 미보관), 클라이언트는 HttpOnly + Secure + SameSite=Strict 쿠키 권장 |
| P0 | OAuth 보안 | `state` 파라미터로 CSRF 방지, PKCE 적용, `redirect_uri` 화이트리스트 엄격 검증. 계정 연결은 provider 이메일 검증 확인 후에만(ERD §2 — 이메일 스푸핑 방지) |
| P0 | 인증 실패 대응 | 로그인 5회 연속 실패 시 캡차(API §1), 10회 시 계정 임시 잠금 + 본인 알림. 실패 응답은 "아이디/비밀번호 불일치"로 통일(계정 존재 여부 미노출) |
| P1 | 2FA | TOTP 시크릿 KMS 암호화 저장(ERD §2), 백업 코드 1회용 발급. 관리자·위탁자·고액 보유 유저에게 활성화 유도 |
| P1 | 세션 관리 | 유저가 자신의 활성 세션(기기) 목록을 보고 개별 종료 가능하게. 비밀번호 변경 시 전 세션 만료(API §1.2) |
| P2 | 인증 코드 | `verification_codes`는 해시 저장, 5~10분 만료, 시도 횟수 제한(ERD §2). 코드는 6자리 이상 CSPRNG 생성 |

## 2. 인가 & 권한 분리

| P | 항목 | 내용 |
|---|---|---|
| P0 | 객체 수준 인가(IDOR 방지) | 모든 `/users/me/*`·리소스 조회는 **토큰의 user_id와 리소스 소유자 일치를 서버에서 강제** — URL의 ID만 믿는 조회 금지. 인벤토리/배송지/입찰/환급 전부 해당 |
| P0 | 관리자 분리 | 관리자 페이지는 **별도 도메인 + IP 화이트리스트 + 2FA 필수**(계획서 §6). `/admin/*`는 `role` + `amr: ["mfa"]` 클레임 이중 검증(API §0) |
| P0 | RBAC 세분화 | `admin_permissions.scope`(card/pack/finance/super)로 최소 권한 원칙(ERD §9). 재무 기능(환급 승인·정산·환불 재시도)은 `finance_admin` 이상만 |
| P0 | 오리파 발행 통제 | `oripa_packs.created_by`는 관리자 전용 — 위탁자·일반 유저의 팩 생성은 어떤 경로로도 불가(ERD §13 법적 리스크 노트, `403 ORIPA_CREATION_FORBIDDEN`) |
| P1 | 수평 권한 상승 점검 | 위탁자 API(`/consignors/me/*`)와 일반 유저 API 간 권한 경계 테스트를 CI에 포함 |
| P1 | 민감 정보 마스킹 | 타 유저에게 노출되는 모든 지점(실시간 피드, 입찰 이력, 랭킹)에서 닉네임 마스킹·개인정보 미포함(API §11 WS) |

## 3. 입력 검증 & 인젝션 방지

| P | 항목 | 내용 |
|---|---|---|
| P0 | 스키마 검증 | 모든 요청 바디·쿼리·경로 파라미터는 **Pydantic v2 strict 모드**로 검증 — 타입 강제, 알 수 없는 필드 거부, 금액은 `Decimal`(float 금지) |
| P0 | SQLi | SQLAlchemy ORM 파라미터 바인딩만 사용, 동적 raw SQL 문자열 조립 금지. JSONB 쿼리도 바인딩 경유 |
| P0 | XSS | 유저 생성 콘텐츠(닉네임, 위탁 설명, 분쟁 사유 등) 출력 시 이스케이프. 응답 `Content-Type` 명시, `X-Content-Type-Options: nosniff` |
| P0 | 파일 업로드 | 이미지 업로드(실물 촬영, 분쟁 증빙, 위탁 제출)는 확장자·MIME·매직바이트 삼중 검증, 리사이즈 파이프라인 통과로 원본 메타데이터(EXIF GPS 등) 제거, S3 직접 업로드는 presigned URL + 콘텐츠 타입 제한 |
| P0 | SSRF | 서버가 외부 URL을 가져오는 지점(카드 이미지 동기화, 시세 크롤러)은 허용 도메인 화이트리스트 + 내부망 IP 차단 |
| P1 | 보안 헤더 | HSTS(preload), CSP(스크립트 소스 화이트리스트), `X-Frame-Options: DENY`, Referrer-Policy. CORS는 프론트 도메인 화이트리스트만(계획서 §6) |
| P1 | 웹훅 파싱 | PG 웹훅 `webhook_payload`(JSONB) 저장 시 크기 제한 + 스키마 검증 — 저장 후 재처리 시에도 신뢰하지 않음 |

## 4. 암호화 — 전송·저장·키 관리

| P | 항목 | 내용 |
|---|---|---|
| P0 | 전송 암호화 | 전 구간 TLS 1.2+ 강제(HTTP→HTTPS 리다이렉트 + HSTS), 내부 서비스 간 통신도 TLS 또는 프라이빗 네트워크 격리 |
| P0 | 저장 암호화 | 개인정보 컬럼 단위 암호화 **AES-256-GCM**: 전화번호·배송지(ERD §2), 위탁자 실명·계좌·세금정보(ERD §11), 2FA 시크릿. DB 스냅샷·백업도 암호화 |
| P0 | 키 관리 | 암호화 키는 **KMS**(AWS KMS/GCP Cloud KMS)로 관리 — 애플리케이션 코드·환경변수에 마스터 키 미보관, 키 롤테이션 연 1회 이상, envelope encryption 적용 |
| P0 | 카드 정보 | 카드번호는 어떤 형태로도 저장·로깅 금지 — PG 토큰화로 PCI-DSS 범위 최소화(계획서 §5.2) |
| P1 | 해시 정책 | 검색·중복확인용 값(이메일 등)은 결정적 해시(HMAC-SHA256 + 서버 시크릿) 별도 컬럼 — 암호화 컬럼은 인덱싱 불가하므로 |

## 5. 결제·지갑 보안

| P | 항목 | 내용 |
|---|---|---|
| P0 | 웹훅 서명 검증 | PG 웹훅은 HMAC-SHA256 서명 재계산 대조 후에만 처리, 불일치 즉시 401(API §5). 웹훅 엔드포인트는 PG IP 대역 화이트리스트 추가 |
| P0 | 금액 서버 재검증 | 웹훅 금액 ≠ 원 요청 금액이면 `AMOUNT_MISMATCH` 처리 + 관리자 알림(API §5) — 클라이언트가 보낸 금액은 절대 신뢰하지 않음 |
| P0 | 멱등성 | 충전/뽑기/환불/입찰 등 모든 금전 변동 API는 `Idempotency-Key` 필수(API §0), DB UNIQUE 제약으로 이중 강제(`pg_tid`, `ledger.idempotency_key`, `pg_refund_tid`) |
| P0 | 원장 무결성 | 잔액은 `ledger_entries`에서만 파생(ERD §7) — `wallets` 직접 UPDATE 금지(트리거/함수 경유), 정합성 배치가 `SUM(ledger) == balance` 상시 대조, 불일치 시 즉시 알림 + 해당 지갑 동결 |
| P0 | 환금성 통제 | `exchange_balance`는 현금 인출 경로에서 완전 배제(ERD §7·§13) — 코드 리뷰 시 환불 계산에 exchange가 섞이는지 필수 점검 항목 |
| P0 | 환불 상한 검증 | `payment_refunds`는 트랜잭션 내에서 `paid_balance` 및 원거래별 취소 가능 잔액 검증(ERD §14.3), 보너스 회수(clawback) 누락 금지 |
| P1 | 이상거래 탐지(FDS) | 단시간 대량 충전/환불 반복, 다계정 동일 결제수단, 신규 계정 고액 충전 룰 기반 알림(계획서 §5.2) — 임계치 초과 시 자동 보류 + 수동 심사 |
| P1 | 경매 홀드 정합성 | `wallet_holds` 활성 합계가 잔액을 초과하지 않는지 배치 검증, 고아 홀드(경매 종료 후 미해제) 자동 회수 |

## 6. 뽑기 엔진 & 랜덤니스 보안

| P | 항목 | 내용 |
|---|---|---|
| P0 | CSPRNG 강제 | 난수는 **`secrets` 모듈만** 사용(`random` 금지 — CI에 lint 룰로 강제), 셔플·슬롯 추출·인증코드·토큰 생성 전부 해당(계획서 §4.2) |
| P0 | server_seed 보호 | `server_seed`는 리빌 전까지 **KMS 암호화 상태로만 저장**, 접근 가능 인원 최소화, 조회 시 `audit_logs` 기록 — 시드 유출 = 매핑 역산 가능이므로 최고 등급 시크릿으로 취급 |
| P0 | 커밋 후 불변성 | `on_sale` 이후 슬롯-실물 매핑 변경 API 자체가 부재(API §7.3) — DB 레벨로도 UPDATE 차단 트리거. 변경 시도는 즉시 보안 이벤트 |
| P0 | 뽑기 로그 불변성 | `draw_logs`·`audit_logs`·`user_change_logs` append-only — 앱 DB 계정에 UPDATE/DELETE 권한 미부여(ERD §14.3) |
| P1 | 검증 도구 공개 | Provably Fair 검증 스크립트를 공개 저장소로 제공 — 유저가 직접 커밋-리빌을 재계산할 수 있어야 신뢰 장치로 기능 |
| P1 | 내부자 위협 | 관리자라도 판매 중 팩의 잔여 슬롯-실물 매핑을 조회할 수 없게 API 미제공 — 운영상 필요한 잔여 등급 수량 집계만 노출(API §3과 동일 수준) |

## 9. 인프라 & 시크릿 관리

| P | 항목 | 내용 |
|---|---|---|
| P0 | 시크릿 관리 | DB 비밀번호·API 키·JWT 서명키는 **Vault/SSM Parameter Store**로만 — 코드·환경파일·이미지에 하드코딩 금지, 저장소 커밋 차단(pre-commit secret scan + GitHub secret scanning) |
| P0 | 네트워크 분리 | DB·Redis는 프라이빗 서브넷(퍼블릭 접근 불가), 관리자 도구는 VPN/제로트러스트 경유. 보안그룹 최소 개방 |
